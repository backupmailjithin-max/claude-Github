# Windows Packaging Certification - Review & Checklist (2026-10-22)

Scope: deep review of `packaging/windows/install.js` and `uninstall.js` (installer logic, NSSM service registration, the new dedicated service account and its ACLs), plus a certification checklist of what's verified vs. what still needs a real Windows machine before release. No code is printed here per project instructions; findings are described, not pasted.

## Bugs found and fixed in this pass

| # | Finding | Why it matters | Fix |
|---|---|---|---|
| 1 | **`secedit /export` output was read/written as UTF-8.** `secedit` writes its `.inf` file as UTF-16LE (with a BOM), not UTF-8. Reading it as `'utf8'` would misinterpret the content; writing it back as `'utf8'` would hand `secedit /configure` a file it doesn't recognize. | This was in the new "log on as a service" rights-granting code - on real Windows this would very likely have made `grantServiceLogonRight` either silently grant nothing correctly, or make `secedit /configure` fail outright, which would have stopped every install/upgrade/repair cold the first time a release relying on this path was tested. | Read and write the temp `.inf` as `'utf16le'`. Verified with a local simulation (`secpol-sim.js`, not shipped) that replays the exact regex/insert/append logic against a realistic UTF-16LE-encoded `.inf` sample, including the "right doesn't exist yet", "right exists with other accounts" (must append, not overwrite), and idempotency (re-running doesn't duplicate) cases - 10/10 checks pass. Also confirmed the *old* code's `'utf8'` read of the same file does NOT recover the `[Privilege Rights]` section, proving the bug was real. |
| 2 | **`(OI)(CI)` inheritance flags applied to plain files.** The read-only-code deny loop used `(OI)(CI)` (object-inherit/container-inherit - directory-only flags) unconditionally for every protected path, including plain files (`server.js`, `package.json`, `package-lock.json`, `integrity.manifest.json`, the HTML entry points, the compiled JS bundles). `icacls` rejects `(OI)(CI)` on a non-container target. | Every one of those file-level deny calls would have failed, and the failure was silently swallowed (the call's result wasn't checked) - so `server.js`, `package.json` and (critically) `integrity.manifest.json` itself would NOT actually have gotten the write-deny the design intends, while directories (`lib`, `node_modules`, `tools`) would. A misused/compromised app process could then still rewrite its own manifest and the files it protects. | Branch on `fs.statSync(path).isDirectory()`: directories keep `(OI)(CI)(...)`, files get the same rights with no inheritance flags. Verified with a local simulation (`acl-sim.js`) against a realistic mixed file/directory tree - every file gets the no-inheritance form, every directory keeps `(OI)(CI)`, and paths that don't exist in a given build (e.g. no `tools/` in a minimal tree) are correctly skipped rather than erroring. |
| 3 | **Deny-ACL failures were silently swallowed.** The per-path `icacls /deny` call's result was never checked at all (not even logged). | An administrator reviewing the install log would see "Applied read-only-code ACLs... (N paths locked)" even if some or all of those calls had failed - a false sense of protection, discovered only by the bug above. | Now checks each call's exit status, counts real successes, and logs a named `WARNING` listing which paths did NOT get locked, with the manual `icacls` command to check them. |
| 4 | **`uninstall.js` never removed the `DcimSvc` service account.** Uninstalling DCIM (with or without `-PurgeData`) stopped and removed both Windows services but left the dedicated service account behind as an orphaned local user - no logon rights, but a stale account nonetheless, and a legitimate finding for a security review of a clean uninstall. | Added removal of the `DcimSvc` local account right after the DCIM service itself is removed (independent of `-PurgeData`, which is about data files, not the account), with a non-fatal warning and the manual command if it fails. |

None of these fixes touch licensing, activation, or anything outside `packaging/windows/install.js`/`uninstall.js`.

## Reviewed and found correct (no change needed)

- **ACL evaluation order**: explicit DENY ACEs on `lib/`, `node_modules/`, etc. are placed directly on those paths, while the broad ALLOW is only on the parent `webapp/` folder and reaches them by inheritance. Windows NTFS always evaluates explicit ACEs before inherited ones and DENY before ALLOW among explicit ACEs at the same level, so the deny correctly wins regardless of call order.
- **`SeDenyNetworkLogonRight`/`SeDenyInteractiterLogonRight`/`SeDenyRemoteInteractiveLogonRight`**: these deny *inbound authentication to this computer as this account* (e.g. over SMB), not the account's own process making or accepting ordinary TCP connections - so denying them does not stop the DCIM service from serving HTTP or connecting outbound to a database.
- **Password reset on every run**: `ensureServiceAccount()` generates a fresh password on every install/upgrade/repair and immediately re-registers it with NSSM's `ObjectName` before the service is ever started - there's no window where the service is registered with a stale password, and nothing needs to persist the password between runs.
- **Service-account creation vs. "log on as a service" right**: the right is tied to the account's SID, not its password, so a password reset never needs re-granting it; `grantServiceLogonRight` is still safely idempotent on every run (checked by regex before inserting).
- **Order inside `installWindowsService`**: service removed first, account ensured + ACLs applied, service re-installed with `ObjectName` set, *then* started - the service is never briefly live as LocalSystem or with a mismatched password.
- **Inno Setup payload**: `lib/vendor/bytenode` and any compiled `.jsc` files are not in the installer's `Excludes` list, so they ship correctly when Bytenode packaging is used; the installer runs elevated (`PrivilegesRequired=admin`), so `install.js`'s own `net`/`icacls`/`secedit` child processes inherit that elevation without a separate UAC prompt.

## Pre-existing gap noted, not fixed (out of this review's scope)

- **No Windows Firewall rule is created** for the DCIM port (or the embedded MariaDB port) anywhere in the installer. This predates the service-account change (LocalSystem would have had the identical gap) and isn't introduced by it, but it's worth fixing before a release that expects the dashboard to be reachable from other machines on the network out of the box - right now a fresh install may be unreachable from anywhere but `localhost` until an administrator (or a GPO) opens the port.

## Dependency note

`grantServiceLogonRight` resolves the new account's SID via a single inline `powershell -NoProfile -Command` call (one .NET `NTAccount`/`SecurityIdentifier` translation, no script file, no module import). This is a narrower use of PowerShell than the full `.ps1` installer this project deliberately replaced (whose failures came from `Import-Module` side effects and script-wide execution-policy/escaping issues, not from a single inline command) - but it is still a PowerShell dependency. Windows PowerShell 5.1 ships by default on every supported Windows Server/Desktop edition, including Server Core, so this should be safe in practice; flagging it so it gets exercised specifically on Server Core during real-hardware validation rather than assumed.

## Certification checklist

| Area | Verified here (code review / logic / simulation) | Still needs a real Windows machine |
|---|---|---|
| Argument parsing, mode selection, disk/port/write-permission checks | Yes (`parseArgs` unit-tested; logic reviewed) | Low risk - mostly pure logic already exercised on real hardware per the code's own history comments |
| `.env` writing, `INTEGRITY_MODE=enforce` default, upgrade/repair never touching `.env` | Yes (reviewed in the prior licensing phase) | - |
| NSSM service registration/removal, `AppExit`/`Start` flags | Reviewed; matches prior real-execution fixes noted in the code's own comments | Yes - this review did not re-execute NSSM |
| Dedicated `DcimSvc` service account creation/password reset | Reviewed; `net user` usage is standard | **Yes** - account creation, password complexity acceptance, and `/passwordchg:no` behavior need a real run |
| "Log on as a service" grant + deny-logon rights via `secedit` | UTF-16LE bug found and fixed; replay-tested against simulated `.inf` content (10/10) | **Yes** - `secedit /export`/`/configure` themselves, and the PowerShell SID lookup, have not run on real Windows |
| Read-only-code ACLs (`icacls` grant + per-path deny) | File-vs-directory bug found and fixed; replay-tested against a simulated mixed tree (6/6) | **Yes** - `icacls` itself has not run; in particular, confirm the DCIM service (running as `DcimSvc`) can actually start the app (read `server.js`/`lib/`/`node_modules`) and write `uploads/`, `backups/`, `logs/`, `.env`, `license.lic` |
| Service actually running as `DcimSvc`, not LocalSystem | Code change present and reviewed | **Yes** - confirm via Task Manager/`sc qc DCIM` on a real box, and confirm the app still passes its own health check end to end under the restricted account |
| Embedded MariaDB (`-EmbeddedDb`) service, account bootstrap, backup/restore | Not touched this pass (runs as LocalSystem still, untouched) | Carries over prior "not executed" status unchanged |
| Uninstall (service + account removal, `-PurgeData`) | Account removal added and reviewed | **Yes** - confirm the account is actually gone and no file lock/permission error blocks removal (the ACL denies on the uninstalling admin's own session should not apply - admins aren't the restricted account - but worth confirming) |
| Code signing / SmartScreen reputation | Not applicable to this review | Needs a real EV/OV code-signing certificate and, for SmartScreen reputation, a signed binary actually circulating - no sandbox can simulate this |
| Windows Firewall rule for the DCIM port | Gap identified, not fixed | Recommend fixing before a release that should be reachable from the network by default |

## Recommendation

The two real bugs found here (UTF-16LE misread, and the file-vs-directory ACL flag mistake) would very likely have caused the new service-account hardening to fail partially or completely on first real use - exactly the kind of thing this review was meant to catch before it reached a real machine. With those fixed, the code is ready for its first real-hardware run; nothing else found in this pass needs further sandbox-side work. Treat the "still needs a real Windows machine" column above as the actual pre-release checklist, and add the firewall rule as a small follow-up before counting Windows packaging as release-ready.
